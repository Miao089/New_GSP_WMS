# New GSP WMS 第一阶段目的物

> 阶段定位：需求收敛 + 最小可验证原型准备。  
> 原则：遵循第一性原则，以最小交付物验证核心业务闭环，避免过早复杂化。

## 1. 第一阶段目标

第一阶段不追求完整系统上线，而是完成后续研发可依赖的基线：

1. 明确系统边界、核心角色、核心业务对象与主流程。
2. 建立可落地的研发生命周期规划，包括阶段、目的物、验收标准和风险控制。
3. 形成 WMS + GSP 合规场景下的最小业务闭环设计。
4. 为第二阶段原型开发准备清晰的模块拆分、数据模型草案和接口边界。

## 2. 业务假设

当前阶段按以下假设推进，后续可通过调研和原型验证修正：

- 系统面向药品 / 医疗器械等受 GSP 或类似质量管理要求约束的仓储业务。
- 核心关注入库、在库、出库、追溯、质量状态和单据留痕。
- 第一阶段优先保证业务闭环、合规留痕和可扩展架构，不优先追求复杂自动化。
- 系统应支持后续与 ERP、监管平台、扫码设备或自动化仓储设备集成。

## 3. 第一阶段目的物清单

| 编号 | 目的物 | 内容范围 | 验收标准 |
| --- | --- | --- | --- |
| D1 | 需求边界说明 | 系统目标、非目标、用户角色、核心业务对象 | 能明确回答“系统先做什么、不做什么” |
| D2 | 业务流程草案 | 入库、上架、库存调整、拣货、复核、出库、追溯 | 每条流程都有触发条件、关键节点、输出单据 |
| D3 | 模块拆分草案 | 基础资料、库存、入库、出库、质量、追溯、系统管理 | 模块职责清晰，边界不重叠 |
| D4 | 数据模型草案 | 商品、批号、库区库位、库存台账、单据、质量状态 | 能支撑最小业务闭环和追溯查询 |
| D5 | 原型范围说明 | 第二阶段原型需要实现的页面和接口范围 | 能直接转化为开发任务 |
| D6 | 风险与约束清单 | 合规、数据准确性、权限、审计、集成、性能 | 每项风险有规避策略或后续验证方式 |

## 4. 最小业务闭环

第一阶段定义的最小闭环如下：

```text
基础资料维护
  -> 采购/入库单创建
  -> 到货验收
  -> 批号与质量状态确认
  -> 上架到库位
  -> 库存台账形成
  -> 销售/出库单创建
  -> 拣货
  -> 复核
  -> 出库确认
  -> 批号追溯查询
```

该闭环是后续原型的优先实现路径。所有非闭环必要能力，例如复杂波次、智能补货、自动化设备调度、财务结算等，暂不进入第一阶段核心范围。

## 5. 角色与职责草案

| 角色 | 核心职责 |
| --- | --- |
| 系统管理员 | 用户、权限、基础配置维护 |
| 仓库管理员 | 库区、库位、库存和作业任务管理 |
| 收货员 | 到货登记、入库验收、异常上报 |
| 质量管理员 | 批号质量状态、放行、冻结、解冻、退货判定 |
| 拣货员 | 按出库任务完成拣货 |
| 复核员 | 出库复核、差异确认 |
| 业务/客服人员 | 查询库存、订单状态和追溯信息 |
| 审计/监管查看者 | 查看留痕、追溯链路和操作记录 |

## 6. 模块拆分草案

### 6.1 基础资料

- 商品 / 物料资料
- 供应商与客户资料
- 仓库、库区、库位
- 批号、有效期、温层、存储条件

### 6.2 入库管理

- 入库单创建
- 到货登记
- 验收记录
- 上架任务
- 入库差异处理

### 6.3 库存管理

- 实时库存
- 批号库存
- 库位库存
- 库存冻结 / 解冻
- 库存调整
- 库存台账

### 6.4 出库管理

- 出库单创建
- 拣货任务
- 复核确认
- 出库确认
- 出库差异处理

### 6.5 质量与合规

- 批号质量状态
- 首营 / 资质资料关联，作为后续增强项
- 操作审计日志
- 单据流转留痕
- 异常处理记录

### 6.6 追溯查询

- 按商品追溯
- 按批号追溯
- 按单据追溯
- 按客户 / 供应商追溯

### 6.7 系统管理

- 用户管理
- 角色权限
- 参数配置
- 字典配置

## 7. 数据对象草案

第一阶段只定义核心对象，不展开完整字段：

| 对象 | 说明 |
| --- | --- |

| InventoryLedger | 库存流水台账 |
| InboundOrder | 入库单 |
| InboundReceipt | 到货 / 验收记录 |

| OutboundOrder | 出库单 |

| AuditLog | 操作审计日志 |

## 8. 第一阶段验收标准

第一阶段完成后，应满足以下标准：

1. 能用一页图或一份文档说明系统核心闭环。
2. 能明确第二阶段原型需要开发哪些页面、接口和数据表。
3. 能识别 GSP / 合规相关的关键留痕点。
4. 能把研发工作拆分为可执行任务，进入迭代开发。
5. 需求变更可以落到模块、流程或数据对象层面，不再停留在口头描述。

## 9. 第二阶段输入

第一阶段完成后，第二阶段应直接使用以下输入：

- 最小业务闭环
- 模块拆分草案
- 数据对象草案
- 原型范围说明
- 风险与约束清单

第二阶段建议目标：实现一个可演示的纵向切片原型，覆盖“入库 -> 库存 -> 出库 -> 追溯”的主路径。

## 10. 风险与后续验证

| 风险 | 影响 | 第一阶段处理方式 |
| --- | --- | --- |
| 合规要求不完整 | 返工、审计风险 | 先标记关键留痕点，后续补充法规映射 |
| 业务流程差异大 | 原型偏离真实作业 | 先聚焦通用闭环，预留配置能力 |
| 数据模型过早复杂 | 开发成本上升 | 只定义核心对象和关系 |
| 权限模型过粗 | 后续安全风险 | 先定义角色，第二阶段再细化权限点 |
| 集成边界不清 | 后续对接困难 | 第一阶段只定义集成候选，不承诺实现 |
